Documentation 六眼

Install, configure and use Rikugan — the reverse-engineering agent that lives inside IDA Pro and Binary Ninja. Rikugan is a native C++ plugin with its own reversing tools, prompts, modes, skills and chat. The general agent machinery underneath (providers and logins, sessions, compaction, MCP) is libomc, linked in-process.

Requirements

  • IDA Pro 9.3 (Hex-Rays for the decompiler tools) or Binary Ninja (UI mode)
  • Linux, macOS or Windows 10/11 x64
  • At least one model: an account login, an API key, or a local server
ℹ️
On Windows, the agent's shell tool runs Git Bash when Git for Windows is installed, else PowerShell.

Installation

Install the release

curl -fsSL https://raw.githubusercontent.com/buzzer-re/Rikugan/main/install.sh | bash      # Linux, macOS
irm https://raw.githubusercontent.com/buzzer-re/Rikugan/main/install.ps1 | iex              # Windows

The installer downloads the prebuilt plugin of each host it finds from the GitHub release, checks it against its .sha256 and unpacks it into the host's plugins folder (--binja-only, --ida-only, --version X.Y.Z; on Windows -Target, -Version). A Rikugan 1.x (Python) install of the same host is moved to ~/.rikugan-1.x-backup/ first.

HostPlugin
IDA Pro (Linux, macOS)~/.idapro/plugins/rikugan.so (.dylib on macOS)
IDA Pro (Windows)%APPDATA%\Hex-Rays\IDA Pro\plugins\rikugan\ (rikugan.dll, libomc.dll, ida-plugin.json)
Binary Ninja (Linux)~/.binaryninja/plugins/librikugan.so
Binary Ninja (macOS)~/Library/Application Support/Binary Ninja/plugins/librikugan.dylib
Binary Ninja (Windows)%APPDATA%\Binary Ninja\plugins\rikugan.dll, with libomc.dll in plugins\rikugan\

Or build it

git clone --recursive https://github.com/buzzer-re/Rikugan
git clone https://github.com/buzzer-re/Oh-My-C ohmyc     # libomc, next to Rikugan
cd Rikugan && ./build.sh && ./install.sh --from dist      # Windows: .\build.ps1; .\install.ps1 -From dist

The build scripts fetch the official Qt headers matching each host (Qt 6.11.1 for Binary Ninja, 6.8.2 for IDA 9.3), build the plugins and write the release packages to dist/. Linux and macOS need CMake, a C++20 compiler, the OpenSSL 3 and zlib headers, curl, and bsdtar or 7-Zip (Debian/Ubuntu: sudo apt install build-essential cmake ninja-build libssl-dev zlib1g-dev libarchive-tools curl; macOS: the Xcode command line tools and brew install cmake openssl@3). Windows needs Visual Studio 2022 or later with Desktop development with C++, and builds libomc through WSL or MSYS2, or takes it from omc's release (.\build.ps1 -OmcVersion latest). Hosts are looked up in their default places; BN_INSTALL_DIR, IDA_DIR and OMC_DIR point elsewhere.

Pick a model

Open the panel (Ctrl+Shift+I in IDA, the Rikugan sidebar icon in Binary Ninja) and follow Connect a model: sign in with a subscription, paste an API key, use a local server, or reuse the logins of an omc agent already on this machine, then pick the model. No restart is needed. Ctrl+M switches models later, and Settings → Provider holds the same choices plus custom connections.

⚠️
Binary Ninja plugins are tied to its API version: after a Binary Ninja update, install the matching Rikugan release or rebuild.

Provider & Model

In Settings → Provider, pick a provider, connect it, then pick its model:

  • Provider — every provider and account plan Rikugan supports (Claude, ChatGPT/Codex, Gemini, Copilot, OpenRouter, DeepSeek …). A dot marks the ones that are ready to use.
  • Account — Log in opens the browser for OAuth (the login sheet shows the link too, with a device code when the provider uses one). Log out removes the stored login or key.
  • API Key — paste a key and press Save key instead of logging in.
  • Model and Thinking — the selected provider's models, listed once it is connected (Refresh reloads them). Leave the model empty to use the first one you have access to. The model pill in the composer switches the model of the current chat.
  • + / − — add or remove a custom connection: any OpenAI-compatible (completions or responses), Anthropic-messages or Ollama endpoint, with its base URL, key and model ids. New or changed connections take effect after restarting the host.
  • Also use the logins of the omc command-line agent — if you use omc outside Rikugan (~/.omc/agent), the providers you logged into there are copied to Rikugan and refreshed OAuth tokens stay in step. Keys added in Rikugan are never copied back and nothing is deleted.
  • Discover local model servers — find Ollama, LM Studio or llama.cpp on this machine (takes effect after a restart).

Logins and keys are stored in ~/.rikugan/omc/agent/auth.json (mode 0600).

Chats

Chats belong to the open database, and reopening a database restores them. A chat keeps working while you look at another file or close the panel, and it ends when you close its database. A chat is named after its first exchange (the way omc names its sessions) unless you rename it. In Binary Ninja, when no file is open, the panel offers Open a binary… and your recent chats. Picking a chat opens its file and continues that chat.

  • Switch chat with the title in the header (searchable) and start a New chat with +. Fork, Rename, Export (Markdown, or HTML with /export) and Delete are in the header menu.
  • The transcript is a timeline: your messages, each step of the agent with its thinking, every tool call (click an address or symbol to jump there, a tool row to see its arguments and result, Undo on a database change), subagents with their live progress, and the cards that wait for you (permissions, approvals, questions, plans).
  • The strip under the header shows what the agent is doing, its todo list, its agents, the /goal it works toward (Pause, Clear) and the running mode. The status line shows the model, context use, tokens, cost and the cursor.
  • / opens the command list, Ctrl+K every command and action, Ctrl+M the model and thinking level (with "Connect a provider…" for logins), Ctrl+J the agents panel, Ctrl+N a new chat.
  • A subagent's whole conversation opens like a chat: double click it in the agents panel, press Open chat, or pick it in the chat list, where each chat lists its agents under it (those working on other databases too). Typing there steers that agent. Back to chat returns.
  • A message sent while the agent works reaches it at its next step, so you can steer a running task. Stop (or Escape) aborts the turn and drops what waits. A message you type while a subagent works ends that subagent early (the agent gets what it found so far) so your message is read at the next step. Send now on a waiting message stops the current step and sends it at once. /btw asks a side question without stopping it.
  • In Binary Ninja the agent can open another file from disk in the background (you approve it first), list the databases open in Binary Ninja, and hand a task to a subagent that reads another database with its own tools. Your current view does not change.
  • Each message carries the cursor address and function unless auto context is off. Context compaction and retries are automatic (/compact and /retry by hand).
  • Colours follow the host's theme, light or dark, also when you switch it.
  • Many chats can stay open. Idle ones beyond four close their agent session and resume it when you return.

Modes

Modes run a sequence of prompts on the current chat. Read-only phases refuse every tool that changes the database, and decisions appear as cards in the chat.

Plan — /plan

/plan Rename all functions in the crypto module with meaningful names
  1. The agent writes a numbered plan without tools.
  2. You Approve, or Reject and then Regenerate (with optional feedback) or Cancel.
  3. Each step runs with progress shown on the plan card.

Explore — /explore

Read-only investigation. The agent logs structured findings (function purposes, constants, data structures, hypotheses) with exploration_report until it is done or the exploration turn limit (Settings → Behavior) is reached, then a knowledge summary is posted.

Modify — /modify

/modify Change the score constant from 100 to 999
  1. Explore — a subagent investigates in isolation and reports findings. Moving on needs at least one function-purpose finding with an address and one high-relevance hypothesis.
  2. Plan — the findings become a numbered modification plan for your approval.
  3. Execute — each change is applied and verified (at most 20 changes).
  4. Save — a card lists the patches: Save keeps them, Discard writes the original bytes back.

Research — /research

Explores, then writes Obsidian-compatible notes (wiki-links, tables, mermaid diagrams) to <database dir>/notes/<genre>/ with an index.md.

Undo

Every tool call that changes the database is recorded in the chat's mutation log. A reversible change shows Undo on its tool row (changes are undone newest first, so undoing an older one also reverts the ones after it), and the header menu has Undo last database change.

/undo        # undo the last change
/undo 5      # undo the last 5 changes

Reversible: rename_function, rename_variable, set_comment, set_function_comment, set_pseudocode_comment, rename_address, set_function_prototype. Scripts, type creation and application, byte patches and IL/microcode transforms are recorded as irreversible. Files the agent writes are not undone.

Turn on Require approval for mutating tools (Settings → Behavior) to confirm each change before it happens.

Script Approval

execute_python (and the other tools that run model-written code, such as IL workflows and microcode optimizers) always asks first. The card shows the code, then choose Allow, Always allow for this chat, or Deny.

⚠️
Scripts run in the host's own Python (IDAPython / Binary Ninja's interpreter) behind a guard that blocks dangerous modules and builtins. The guard is a blocklist, not a sandbox. The agent never runs the target binary.

Files & Shell

The agent can read, write and edit files, search them, run shell commands, search the web and keep a todo list, so a session can produce scripts, notes and patches as well as annotations. Each kind of access (reading files, writing, editing, shell commands) asks the first time in a chat: Allow once, Allow for this chat (the chat's subagents included) or Deny. Settings → Behavior can allow file access or shell commands without asking.

The agent's working directory is a per-database scratch folder (~/.rikugan/scratch/<db id>/). The binary's folder is reachable by path.

⚠️
File and shell tools are not sandboxed and file changes are not undone by /undo. A hostile sample can try to steer any agent with prompt injection, so weigh that before allowing shell commands for a sample you don't trust.

Subagents & Bulk Renamer

The agent can delegate with spawn_subagent: an isolated session with its own context that uses the same host tools, approvals, permissions and undo log, and returns a summary. Its progress shows in the transcript. The agents panel (Ctrl+J, or click an agent) lists the chat's agents as a tree with each one's live log, Stop, Steer (a message to a running agent), Send summary to chat and + New agent (preset, perks, turn budget).

The bulk renamer (header menu → Bulk renamer) renames functions in bulk. Pick functions from the table (filters and search make auto-generated names such as sub_/FUN_ easy to select) or send them with Send to Bulk Rename. Quick mode sends batches of decompiled functions to tool-less model calls (batch size and concurrency in Settings → Behavior). Deep mode runs one subagent per function. Pause, resume, stop and Undo All are available.

MCP Servers

Add MCP servers in Settings → MCP: a stdio command (with arguments and environment) or a URL (with headers). They are stored in ~/.rikugan/omc/agent/mcp.json and their tools are offered to the agent next to Rikugan's. A server can be disabled without removing it. /mcp lists the configured servers.

{
  "mcpServers": {
    "my-server": {
      "command": "my-mcp-server",
      "args": ["--stdio"],
      "env": {}
    },
    "remote": {
      "type": "http",
      "url": "https://example.com/mcp"
    }
  }
}

Project-level MCP files are ignored, so a sample's directory cannot add servers.

Binary Ninja's own MCP server

Binary Ninja can run an MCP server of its own (turn on ui.mcp.enabled in Binary Ninja's settings and restart). When it is running, Rikugan offers its tools the first time a database shows. Use them switches that database's chats to Binary Ninja's bn_* tools, and No leaves Rikugan's tools in place. The MCP button in the panel header switches between the two at any time. If the server was stopped, the button offers to start it. The answer is remembered for each database.

While Binary Ninja's tools are on, Rikugan's own analysis tools are hidden for that database, so the model sees one tool set and not two. Every call acts on the chat's own database, even with other files open. Changes made with these tools go through the same approval and mode rules as Rikugan's, but /undo cannot revert them. Turn the button off to get Rikugan's tools and their undo back. The address, port and token come from Binary Ninja's ui.mcp.port, ui.mcp.endpoint and ui.mcp.token settings, and the port must not be 0.

Custom Skills

Put your own skills in ~/.rikugan/omc/agent/skills/:

my-skill/
  SKILL.md             # required: frontmatter + instructions
  references/          # optional: extra .md files the skill can point to
    api-notes.md
---
name: my-skill
description: What it does in one line
mode: plan            # optional: plan | exploration
---
Task: <instruction for the agent>

## Approach
1. First step...
2. Second step...
FieldDescription
nameThe skill id, matching the folder name (/my-skill)
descriptionOne line shown to the model and in autocomplete
modeOptional: plan starts /plan, exploration starts /modify, with the skill as instructions

A folder with the same name as a built-in skill takes its place. Built-ins can be turned off in Settings → Skills.

Persistent Memory

RIKUGAN.md next to your IDB/BNDB keeps findings across sessions:

  • The agent saves facts with the save_memory tool (categorized: function purpose, architecture, naming convention, data structure …).
  • The first 200 lines are loaded, sanitized, into the system prompt of every new session.
  • /memory shows the current contents.

Profiles

Profiles control what data reaches the model and which tools it may use. default and private are built in, and you can create, clone or delete your own in Settings → Profiles.

  • Hide binary metadata — no binary summary, cursor or function name in prompts.
  • IOC redaction — hashes, IPv4/IPv6, domains, URLs, registry keys, file paths, emails, crypto wallets, mutex names are replaced in every tool result.
  • Custom filter rules — your own regex or literal patterns with replacements.
  • Denied tools and denied functions — tools the model never sees and functions it must not analyze.
  • Prompt filters and a description added to the system prompt, plus singular analysis to keep the agent on one binary.
