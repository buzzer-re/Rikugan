01

Overview

Rikugan 2.x is a native C++20 / Qt Widgets plugin for IDA Pro 9.3 and Binary Ninja (Linux, macOS). The agent — turn loop, providers and logins, session files, compaction, retries, skills, MCP and the file/shell/search tools — is libomc (oh-my-c), linked into the plugin. Rikugan supplies the reverse-engineering half: host analysis tools, the chat panel, per-database chats, undo, modes, subagents with host tools, the bulk renamer, analysis profiles, prompts and skills. Rikugan 1.x was a Python plugin; it remains in the git history.

  • Host (src/common/host/Host.h) is everything shared code needs from one open database: paths, a stable database id (IDA netnode $ rikugan, BN metadata rikugan_db_id), cursor, navigation, runOnMainThread, decompiler presence, binary summary, registerTools, the host's own Python, byte read/write. IdaHost and BnHost implement it.
  • DbContext is created on the UI thread when the panel first shows a database; it registers the host's analysis tools and Rikugan's chat tools and owns the database's chat index.
  • PanelCore is the panel: header (chat switcher, Ctrl+K command palette, new chat, menu), activity strip (what the chat does now, agents, todo, goal, mode), transcript, agents panel, composer (slash commands, Ctrl+M model picker, queued prompts) and status line, plus the bulk renamer page, the login sheet, Get Started (shown while no model can answer) and Settings. Hosts feed it the current database, cursor moves and context-menu actions (agent/Actions.h).
  • Theme takes every colour from the host's palette, so the panel matches IDA's and Binary Ninja's light and dark themes and follows a theme switch. In Binary Ninja the address, symbol, status and code colours are its own theme colours too. Elsewhere those come from Rikugan's defaults, corrected for contrast.
  • Transcript. TranscriptModel turns a chat's frames, its replayed history and its cards into flat rows: timeline nodes and the rows of each step (thinking, text, tool calls with address chips, Undo and status, a card per batch of subagents). Streamed text is revealed a few characters per display frame, so a burst flows in over about 100 ms instead of jumping. Consecutive calls of one tool fold into a single row with their count. TranscriptView is a virtualized list whose delegate paints from cached documents, and pending cards are live widgets in their rows.

02

Embedding libomc

  • Prelink. cmake/build_omc.sh builds omc's objects with omc's own Makefile and prelinks them into one relocatable object whose only globals are the omc_* API (ld -r + objcopy --keep-global-symbols; -exported_symbols_list on macOS). omc's internals cannot collide with the host process; the plugin modules export only their entry points.
  • RPC frames. Everything goes through omc's RPC protocol: JSON frames sent with omc_send, received through one event callback per session. Rikugan uses prompt, get_state, get_messages, get_last_assistant_text, set_model, fork, set_event_filter, set_host_tools, the account commands, and the control frames host_tool_result, host_tool_update, extension_ui_response.
  • Host tools. set_host_tools gives omc the JSON schemas of the visible tools. When the model calls one, omc emits host_tool_call and waits for a host_tool_result with the same id; host_tool_cancel aborts it. Mutating, script and Exclusive tools are marked exclusive: omc runs them alone and in message order; the rest may run in parallel.
  • Event filter. Sessions subscribe to turn, message, tool-execution, compaction, retry, queue, model/thinking and notice frames, with messageUpdates:"delta".
  • AgentHome runs once at plugin init: OMC_CONFIG_DIR = ~/.rikugan/omc, local model discovery off unless enabled, a CA bundle for hosts that bundle their own libcrypto, and a managed config.yml (approval mode yolo because Rikugan gates tools itself; sleep prevention, cache warming, skill-description compression, omc memory and project MCP off), plus models.yml from custom endpoints, omc's project prompt and the built-in skills.
  • ServiceSession: one tool-less, in-memory omc session per process for Settings (model lists, login, logout, accounts). Login dialogs arrive as extension_ui_request frames. It opens on rikugan-service/settings, a keyless placeholder in models.yml, because omc refuses a session without a model and Settings must work before any login exists.

Threads

ThreadRunsNever
Host UI / main threadQt widgets, ChatSession, PanelCore, IDA SDK calls, BN UI calls (jump_to)waits on omc, a session worker or a tool worker (except plugin shutdown, after Host::closing is set)

omc event threadsthe callback: peek "type", answer request waiters, queue the raw frameblocks
ToolDispatcher pool (8, process-wide)host tool calls through the pipeline. Blocking tools (ask_user, spawn_subagent) get their own thread—
Host main thread (marshalled)MainThread tools, undo pre-state readers, binary summary—
  • Control frames and omc_abort may be sent from any thread; omc handles them inline, not behind a running turn.
  • Main-thread marshalling. onMain(host, access, f) runs inline on the main thread, otherwise posts a MainThreadCall (IDA: execute_sync with MFF_NOWAIT and MFF_READ/MFF_WRITE; BN: ExecuteOnMainThread) and waits. With Host::closing set, queued calls are abandoned and the caller gets “Rikugan is shutting down”; a call never runs against an abandoned caller's stack. Exceptions are rethrown on the worker.
  • EventQueue. omc threads push() raw frames; the first push into an empty queue posts one DrainEvent to the chat's QObject, which drains everything queued so far. No timers, nothing while idle. Other cross-thread UI updates use queued invokeMethod on uiAnchor(), guarded by QPointer.
  • Cards. Approvals, ask_user and mode decisions block the asking worker until the user answers or the call's CancelToken fires. The UI thread only shows the card.
  • Unload. IDA unloads rikugan.so at exit with its Qt event loop still running, so no plugin thread, posted event or timer may outlive it. Background threads start through spawnThread, and worker results are posted to uiAnchor(), a plugin-owned QObject that also parents module-wide timers.
  • Shutdown (IDA). The plugin sets Host::closing, deletes the panel synchronously, drops the database and widget, shuts down the service session and the tool pool, then joins the spawned threads and deletes the anchor. Closing a database sets Host::closing first so queued main-thread work cannot touch it.

Chat Lifecycle

A prompt
composer -> CommandRouter::submit -> ChatSession::sendPrompt -> worker: OmcSession::prompt
  prompt -> (omc agent loop: model, host_tool_call ...) -> prompt_result -> get_last_assistant_text
omc frames -> SessionListener -> EventQueue -> ChatSession::frame -> chat widgets
  • A chat is an entry in <sessions>/<db id>/chats.json (id, omc session file, title, timestamps, fork parent). omc writes the session file lazily after the first answer.
  • <sessions>/<db id>/database.json records the host and the file the database came from. With no database open, Binary Ninja's panel lists “Open a binary…” and the newest chats. Picking a chat opens its file (or focuses the tab that already shows it) and selects that chat. A binary that was never saved as a database takes the chat's id when it opens from that list.
  • The omc session opens lazily with cwd ~/.rikugan/scratch/<db id>/, the chat's session file to resume, the configured model and thinking level, the system prompt, the omc built-in allow-list and the host tools. On resume the transcript is replayed from get_messages.
  • Live-session limit: at most 4 chat sessions are open per process; idle chats beyond that close (LRU) and resume from their session file on demand.
  • A message typed while the chat works is steered into the running agent (omc steer) and shows as queued until omc's queue_update says it was taken. Commands, and anything a run did not take, go out as the next prompts. Stop aborts the turn and drops both. When a run ends, cards still open are answered “cancelled”. A session omc refused to start (no model yet) opens again on the next prompt. A queued message's Send now stops the run and sends it first.
  • Other databases (Binary Ninja): list_databases, open_database (loaded in the background with BinaryNinja::Load, no tab, after the user approves the path), ask_database (a read-only subagent on another database with that database's tools) and close_database. Each typed prompt gets a <rikugan_context> block (cursor, function) unless auto context is off or the profile hides metadata; /-commands are sent bare so omc recognises them.
  • After each prompt the worker runs AuthSync and posts the cached state (model, context usage). Fork sends fork; changing the model sends set_model. Compaction and retries are omc's.

05

System Prompt

buildSystemPrompt assembles the prompt once per omc session from embedded prompts/system/** files (order and placeholders in prompts/MANIFEST.md):

  1. base.md with the host's intro, tool usage and capabilities.
  2. memory.md: the first 200 lines of RIKUGAN.md, sanitized and capped.
  3. current_binary.md: the host's binary summary through sanitizeBinaryContext (skipped when the profile hides metadata).
  4. available_tools.md: visible host tools plus omc built-ins.
  5. filesystem.md / shell.md for omc's disk tools and bash.
  6. Profile sections: singular analysis, custom instructions, restricted functions, active profile and IOC filters.

omc lists skills itself. Mode instructions travel in the mode's prompts (or a subagent's task addendum); the context block is prepended to each user prompt.

Tools & Pipeline

Kinds

  • Host analysis tools: rk::ToolSpecs added in Host::registerTools (src/binja/tools/, src/ida/host/tools/, SDK subclasses in src/ida/sdk/). Names, descriptions and parameters are kept 1:1 with the 1.x tools.
  • Chat tools: ask_user, save_memory, spawn_subagent (depth 0 only), exploration_report and research_note (while a mode shows them).
  • omc built-ins: read, write, edit, ast_edit, grep, glob, bash, web_search and todo. MCP tools come from omc. omc asks before each disk or shell call and Permissions answers at once when the chat (or a setting) already allows that kind. Otherwise the transcript shows a card: Allow once, Allow for this chat or Deny. A chat's subagents share its answers.
  • Binary Ninja's MCP tools (HostMcp, BnHostMcp): the bn_* tools of Binary Ninja's own MCP server (ui.mcp.enabled), offered per database once the user agrees, through the offer line or the header's MCP button (remembered as hostMcp in database.json). They go through the same dispatcher. A tool whose name has no reading verb is Mutating and is recorded as not undoable. While they are on, Rikugan's host tools are hidden for that database. Calls take turns and first select the chat's view, because the server's active view is global. Toggling closes idle sessions so they resume with the matching system prompt.

Flags: Mutating, MainThread (IDA: every tool; BN: UI and mutating tools), RequiresDecompiler, Cacheable, Script, Internal (undo readers, never shown), Exclusive, Blocking, External (served by another program: Binary Ninja's MCP tools).

07

Undo

  • One MutationLog per chat, in memory, shared with the chat's subagents.
  • Reversible: rename_function, rename_variable, set_comment, set_function_comment, set_pseudocode_comment, rename_address, set_function_prototype. A reversible tool's success text starts with “Renamed”, “Named” or “Set ”.
  • Known irreversible: execute_python, type creation/application, byte patches, IL/microcode transforms, optimizer/workflow installs, redecompile_function.
  • /undo N pops newest first off the UI thread; a reverse that can never succeed is dropped, any other failure stops and keeps the record. File changes made with omc's disk tools are not undone.

Modes

ModeDriver::start runs one busy job on the chat's session worker: prompts in sequence, the phase set in ChatContext (read-only phases refuse mutations), mode-only tools shown with set_host_tools between prompts, turn_start frames counted to cap each phase, decisions asked through cards.

3

Leaving explore in /modify needs a function-purpose finding with an address and a high-relevance hypothesis. ModeState holds findings, functions, patches and notes, shared with the mode's subagents.

09

Subagents & Bulk Renamer

omc's own task subagents cannot see host tools, so Rikugan runs its own: runSubagent opens a separate omc session (session dir subagents/) with the parent's database, tools, approvals, permissions, profile and mutation log, at depth + 1. The task is framed by prompts/agents/subagent.md plus an optional preset (network_recon, report_writer) and perks, and a turn cap aborts runaway runs. SubagentRegistry keeps each agent's live progress (current tool, tools, tokens, a log) for the transcript and the agents panel (tree, log, Stop, Steer, send the summary to the chat, new agent).

Bulk renamer

  • Quick: functions are decompiled one by one (with disassembly), cut to 6,000 chars, packed into batches (batch size and ≤ 180,000 chars) and sent to tool-less, session-less omc worker sessions, up to the concurrency limit at once. Replies are 0x<addr> <name> lines.
  • Deep: one subagent per function (10 turns), answered with RENAME: 0x<addr> <name>.
  • Pause, resume, cancel (aborts in-flight sessions), Undo All. Each batch is a subagent of category bulk_rename.

Settings & Files

RikuganConfig (~/.rikugan/config.json, RIKUGAN_HOME overrides the root) is shared by both hosts. Settings tabs: Provider (one provider at a time: login or API key, then its model and thinking level; custom connections; shared omc logins; local discovery), Behavior, Skills, MCP, Profiles.

Built-in skills are embedded in the plugin and synced into omc/agent/skills/<slug>/ with a .rikugan-builtin version marker; a user folder of the same name is never overwritten.

AuthSync

“Use my omc logins” merges Rikugan's auth.json (R) with standalone omc's (O): providers only in O are copied to R; for an OAuth login in both, the one that expires later wins on both sides; API keys in both keep R's; R-only entries never go to O; nothing is deleted. Writes are atomic and 0600; omc reloads credentials when R changed. It runs after each prompt, after a login and when Settings closes.

Security Model

Rikugan processes adversarial binaries; strings, names and code from the sample reach the model and the UI.

  • Injection. Every host tool result passes stripInjectionMarkers (zero-width characters, role markers, chat template delimiters, the Anthropic magic string, override phrases, homoglyph-normalised), then the profile's IOC filter. Memory and binary context in the system prompt are sanitised and capped. The data-integrity section of the system prompt tells the model tool output is data, not instructions.
  • Scripts. execute_python and the other Script tools always ask, showing the code. They run in the host's own Python after prompts/python/guard_prelude.py (AST blocklist, restricted builtins). The agent never runs the target binary.
  • Disk and shell. omc's file and shell tools ask before their first use in a chat, per kind (read, write, edit, shell). "Allow for this chat" covers the chat and its subagents, and Settings can allow files or shell commands without asking. They are not sandboxed.
  • omc settings isolation. The session cwd is Rikugan's scratch dir, never the sample's directory; project context files, rules and project MCP are off; omc commands that would chdir the host are refused.
  • Credentials live in auth.json (0600); models.yml with endpoint keys is 0600.

Residual risks

  • Sanitisation is pattern-based and cannot catch every phrasing of an injection.
  • With shell access allowed, an injected instruction can reach bash with the user's privileges, and file changes are not undoable.
  • The guard prelude is a blocklist inside the host's Python, not a sandbox; an approved script can do anything the host can. “Always allow” removes the per-script prompt for that chat.
  • MCP servers the user configures run as the user.
