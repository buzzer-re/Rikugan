01

Overview

Rikugan 2.x is a native C++20 / Qt Widgets plugin for IDA Pro 9.3 and Binary Ninja on Linux, macOS and Windows. The agent is libomc (oh-my-c), linked into the plugin: it owns the turn loop, providers and logins, session files, compaction, retries, skills, MCP and the file, shell and search tools. Rikugan supplies the reverse-engineering half, which covers the host analysis tools, the chat panel, per-database chats, undo, modes, subagents with host tools, the bulk renamer, analysis profiles, prompts and skills. Rikugan 1.x was a Python plugin and remains in the git history.

AGENTS.md describes the build, the source layout and the coding rules, DEVELOPMENT.md the contributor workflow, and prompts/MANIFEST.md lists every model-facing text with its placeholders.

  • Host (src/common/host/Host.h) is everything shared code needs from one open database: paths, a stable database id (IDA netnode $ rikugan, BN metadata rikugan_db_id), cursor, navigation, runOnMainThread, decompiler presence, binary summary, registerTools, the host's own Python and byte read/write. IdaHost and BnHost implement it, and host code never leaks into src/common.
  • DbContext (agent/DbContext.h) is created on the UI thread when the panel first shows a database. It registers the host's analysis tools and Rikugan's chat tools, and it owns that database's chat index.
  • PanelCore (ui/PanelCore.h) is the panel. It has a header (chat switcher, Ctrl+K command palette, new chat, overflow menu), an activity strip with what the chat is doing now and its agents, todo, goal and mode, the transcript, the agents panel (Ctrl+J), the composer (slash palette, model picker on Ctrl+M, queued prompts) and the status line. It also holds the bulk renamer page, the login sheet, Settings, and Get Started, which shows while no model can answer and walks the user through signing in, an API key, a local server or the omc agent's logins, then the choice of model. The hosts feed it the current database, cursor moves and the context-menu actions of agent/Actions.h: Explain, Rename, Deobfuscate, Find vulnerabilities, Suggest types, Annotate, Clean microcode/IL, Xref analysis, Send to Rikugan, Smart Patch (Binary Ninja only) and Send to Bulk Rename.
  • Theme (ui/Theme.h) derives every colour from the host's palette, so the panel follows IDA's and Binary Ninja's light and dark themes and switches with them at runtime. The tool-kind, status, address, symbol and code colours come from the host's theme when it names them (setHostColors, fed by Binary Ninja's getThemeColor) and from Rikugan's defaults otherwise, and all of them are contrast-corrected against the host background. The panel's stylesheet is scoped to #rk_root.
  • The transcript lives in ui/transcript/. TranscriptModel reduces a chat's frames, its replayed transcript and its cards into flat rows. Timeline nodes mark the user, each rikugan step, permissions, phases and notices; step rows hold thinking, text, tool calls (with their kind, address and symbol chips, an Undo chip and a status) and one task card per batch of subagents. Consecutive calls of one tool fold into a group row that shows their count. Streamed text is revealed a few characters per display frame, so a burst lands within about 100 ms, and each growing row repaints once per frame. TranscriptView is a virtualized QListView whose delegate paints rows from QTextDocuments cached per row revision and width. Pending cards are live widgets inside their rows.

Embedding libomc

  • cmake/build_omc.sh builds omc's objects with omc's own Makefile and prelinks them into one relocatable object whose only globals are the omc_* API (ld -r + objcopy --keep-global-symbols, or -exported_symbols_list on macOS). omc's internals therefore cannot collide with the host process, and the plugin modules export only their entry points (rk_export_only).
  • On Windows the hosts are MSVC programs (Qt, C++ ABI) while omc builds with MinGW-w64, so libomc stays a DLL. cmake/build_omc_win.cmake runs omc's make WINDOWS=1 through WSL or MSYS2, or takes a prebuilt libomc.dll (OMC_LIB_DIR, for example omc's Windows release), makes an MSVC import library from libomc.def and copies the DLL next to the modules. Only the C API crosses the boundary. Neither host searches the plugin's folder for dependencies, so the plugins delay-load the DLL (/DELAYLOAD:libomc.dll) and rk::loadOmcLibrary (omc/OmcLibrary.h) loads it by full path at plugin init. IDA finds it at plugins\rikugan\libomc.dll. Binary Ninja uses the same plugins\rikugan\libomc.dll, beside plugins\rikugan.dll, because it loads every top-level DLL as a plugin. The loader checks omc_api_version and keeps the DLL loaded for the life of the process.
  • libomc's C runtime on Windows is msvcrt.dll, which keeps its own copy of the environment, so every variable omc reads (OMC_CONFIG_DIR and the others) is set through rk::setEnv, which also calls msvcrt's _putenv_s. In library mode omc installs no crash handler. It adds a console control handler (inert in a GUI host), starts Winsock and sets a 1 ms timer resolution.
  • Rikugan calls the C API at OMC_API_VERSION 2: omc_session_new/free, omc_send, omc_abort, omc_free, omc_version, omc_api_version and omc_set_result_filter. The last one hands Rikugan the text of every tool result, omc's built-ins and MCP tools included, before the model, the session file and the events see it. A libomc of another API version is refused at load.
  • The rest of the conversation with omc is its RPC protocol: JSON frames sent with omc_send and received through one event callback per session. Rikugan uses prompt, get_state, get_messages, get_last_assistant_text, set_model, fork, set_event_filter, set_host_tools, the login and account commands, and the control frames host_tool_result, host_tool_update and extension_ui_response.
  • set_host_tools gives omc the JSON schemas of the visible ToolSpecs. When the model calls one, omc emits host_tool_call and waits for a host_tool_result with the same id; host_tool_cancel aborts the call. Mutating, script and Exclusive tools are marked exclusive, so omc runs them alone and in message order, and the rest may run in parallel.
  • Each session's event filter subscribes to the frames the UI needs (turn, message and tool execution, compaction, retry, queue, model and thinking changes, notices) with messageUpdates:"delta". It does not request agent_end.
  • AgentHome (omc/AgentHome.cpp) runs once at plugin init, before the first session. It points OMC_CONFIG_DIR at ~/.rikugan/omc, disables local model discovery unless the user enabled it, and sets a CA bundle for hosts that bundle their own libcrypto. It writes omc/agent/config.yml with approval mode yolo, because Rikugan asks for tool approval itself, and with sleep prevention, cache warming, skill-description compression, omc memory and project MCP turned off. It also writes models.yml from the custom endpoints, omc's project prompt from prompts/omc/, and the built-in skills.
  • ServiceSession is one tool-less, in-memory omc session per process that Settings uses for model lists, login, logout and accounts. Login dialogs arrive as extension_ui_request frames. omc refuses to open a session without a model, and Settings has to work before any login exists, so the service session opens on rikugan-service/settings. That is a placeholder provider that models.yml always declares without a key, and omc never counts it as available or picks it as a default.

  • The control frames (host_tool_result, host_tool_update, extension_ui_response) and omc_abort may be sent from any thread. omc handles them inline without queueing them behind a running turn.
  • Main-thread marshalling goes through onMain(host, access, f). On the main thread it runs f inline; on any other thread it posts a MainThreadCall and waits. IDA posts with execute_sync, MFF_NOWAIT and MFF_READ/MFF_WRITE from src/ida/sdk/, and Binary Ninja with ExecuteOnMainThread. Once Host::closing is set, queued calls are abandoned and the caller gets “Rikugan is shutting down”, so a call never runs against an abandoned caller's stack. Exceptions thrown on the main thread are rethrown on the worker.
  • EventQueue (omc/EventQueue.h) carries frames to the UI. omc threads push() raw frames, and the first push into an empty queue posts one DrainEvent to the chat's QObject, which drains everything queued so far. A burst costs one coalesced postEvent, with no timers and no work while idle. Other cross-thread UI updates use QMetaObject::invokeMethod(rk::uiAnchor(), ..., QueuedConnection) guarded by QPointer.
  • Approvals, ask_user and mode decisions are shown as cards through the chat's ChatUi bridge. The asking worker blocks on a condition until the user answers or the call's CancelToken fires, and the UI thread only shows the card.
  • IDA unloads rikugan.so / .dll at exit while its Qt event loop is still running, so no plugin thread, posted event or timer may outlive the module (util/ModuleLifetime.h). Background threads start through spawnThread, and workers post their results to uiAnchor(), a plugin-owned QObject that also parents module-wide timers.
  • On IDA shutdown, ~RikuganPlugmod sets Host::closing and deletes the panel synchronously, which also deletes every event posted to its widgets and chats. It then drops the database, closes the widget, runs ServiceSession::shutdown and ToolDispatcher::shutdown, and calls shutdownModule(5000), which joins the spawned threads and deletes the anchor. Closing a database sets Host::closing first so queued main-thread work cannot touch it. Binary Ninja never unloads plugins, and the thread registry is never destroyed, so exiting with threads still running does not terminate.
  • IDA numbers HT_UI and HT_IDB events independently (HT_UI 0 is ui_range, HT_IDB 0 is closebase), so the plugin listens to each with its own listener. With one shared switch, the database closed whenever the disassembly range changed.
  • The crash guard (util/CrashGuard.h) is installed at plugin init. It catches a fault whose instruction is in Rikugan or libomc (on Windows with a first-chance vectored handler, on Linux and macOS with SIGSEGV, SIGBUS, SIGILL and SIGFPE handlers that check the address with dladdr) and a std::terminate on a Rikugan thread, since every thread calls crash::guardThread(). It writes ~/.rikugan/logs/crash-log-<YYYYMMDD-HHMMSS>-<pid>.log with the reason, the address as module + offset, the thread, the versions and the faulting thread's stack. It then saves a recovery copy of each open database beside that database (<db>.rikugan-recovered.i64 / .bndb; the database file itself keeps its last save) on the host main thread, which never waits on Rikugan's threads (30 s deadline), and passes the crash on to the previous handler. Faults in host code are left alone. The next start reports, in the host's log, the crash logs it has not seen yet. IDA removes the handlers at unload.

Chat Lifecycle

A prompt
composer -> CommandRouter::submit -> ChatSession::sendPrompt -> worker: OmcSession::prompt
  prompt -> (omc agent loop: model, host_tool_call ...) -> prompt_result -> get_last_assistant_text
  prompt -> (an omc command that runs without the agent: /compact ...) -> response agentInvoked:false (no prompt_result)
omc frames -> SessionListener -> EventQueue -> ChatSession::frame -> TranscriptModel -> TranscriptView
  • A chat is a ChatEntry in <sessions>/<db id>/chats.json with its id, omc session file, title, timestamps and fork parent. omc writes the session file lazily after the first answer. The title starts as the first prompt. After the first exchange omc names the session the way omc and omp do, with a short side request followed by a notice of level title, and the chat takes that name unless the user renamed it. A name the user gave is marked title_by_user and set on the session when it opens, so omc does not rename it. Sessions that are not chats are named when they open.
  • <sessions>/<db id>/database.json records the host and the file the database came from (RecentSessions; it is rewritten when Binary Ninja saves the database elsewhere). With no database open, a host that gives the panel a file opener (PanelCore::setFileOpener, as Binary Ninja does) lists “Open a binary…” and that host's newest chats. Picking a chat opens its file, or focuses the tab that already shows it, and selects the chat. A binary that was never saved as a database has no stored id, so the panel tells the host which id to take for that file (expectSession).
  • The omc session opens lazily (ensureOpen). Its cwd is ~/.rikugan/scratch/<db id>/ and its session dir <sessions>/<db id>/. It resumes the chat's session file and gets the configured model and thinking level, the system prompt, the omc built-in allow-list and the host tools. On resume the transcript is replayed from get_messages with the context blocks stripped.
  • Chats live in ui/ChatHub, one per process under the module anchor, keyed by database. A panel attaches to the chats of the database it shows and detaches when it turns to another one, so a chat keeps running while the user looks at another file, and IDA's dock can close and reopen without touching it. The host closes a database's chats when it closes that database (ChatHub::closeDatabase) and all of them at unload (closeAll). Closing a chat cancels its mode job and every subagent it started. Host-call cancels are keyed by session and call id, because omc numbers calls per session, so one chat's Stop never reaches another chat's tool.
  • SubagentRegistry keeps every subagent frame (appendFrame) until “Clean” removes the agent. “Open chat” builds a TranscriptModel from those frames with observeFrames, which delivers the frames so far and then each new one, posted to the UI once per burst. The transcript then shows the agent's run like a chat, the composer steers the agent, and the chat switcher lists each chat's agents under it.
  • ChatContext::steerPending counts the user's messages the agent has not taken yet. A subagent started by spawn_subagent or ask_database stops when such a message arrives, and its call returns what it had so far, marked as cut short. The agent then reads the message at its next step, since omc only hands steering over between tool calls. Mode subagents and manual ones keep going.
  • At most 4 chat sessions are open per process. ChatSession::touch keeps an LRU, and idle chats beyond the limit close and resume from their session file on demand.
  • A message typed while the chat works is steered into the running agent (omc steer), which reads it at its next turn. It shows as queued until omc's queue_update says the agent took it. Commands that run a job of their own (modes, /undo, /doctor, a new goal) wait in the queue and go through CommandRouter when the run ends, and anything the run did not take goes out as the next prompt. Stop aborts the turn and drops both. When a run ends, cards still open are answered “cancelled” so nothing keeps the composer locked. A queued message's Send now button stops the run and sends that message first, with the rest after it.
  • On Binary Ninja every DbContext registers itself in agent/Databases.h, and the chat reaches the other databases through three tools. list_databases lists them. open_database opens a file in a new tab through databases::setTabOpener, which calls UIContext::openFilename and then waits for that file's OnAfterOpenFile; the user approves the path first. ask_database runs a subagent on another database with that database's tools, in a read-only phase and with its own undo list. These tools are offered only where the host can open another tab, and never to subagents.
  • A session omc refused to start (no model yet) is opened again on the next prompt, so a model connected afterwards works without restarting the host. Logins and keys reach omc at once, because Rikugan makes it re-read auth.json.
  • Each typed prompt gets a <rikugan_context> block with the cursor address and function, unless auto_context is off or the profile hides metadata. Text starting with / is sent bare so omc recognises its commands.
  • After each prompt the worker runs AuthSync::run() and posts rikugan_prompt_done with the cached state (model, context usage). Fork asks omc to fork and creates a new ChatEntry pointing at the copy. Changing the model sends set_model, and changing the thinking level sends set_thinking_level.
  • Compaction, retries and context limits belong to omc (/compact, /retry), and the chat shows its automatic compaction and retry frames. A command omc runs itself without the agent, such as /compact, answers the prompt with agentInvoked:false and sends no prompt_result; that answer ends the prompt.
  • omc records more user messages than the user typed: goal context, async results, agent steering and [SYSTEM] notes. typedUserText (agent/ChatExport.h) decides which ones are the user's and how they read (a skill reads as /<slug> args). The live transcript, the replayed one and the Markdown export all use it.
  • Settings changes reach open chats through ChatHub::settingsChanged and ChatSession::settingsChanged. An idle chat takes the active profile at once and closes its session, so the next prompt reopens it with the new system prompt, tools and MCP servers. A busy chat does the same when its run ends, because tool workers read the profile while it runs.
  • A panel shows one database at a time. On Binary Ninja it can be the sidebar widget, a pane (“Open in pane”) or the full-window tab; on IDA it is the dock. The header's expand button (PanelCore::setWindowToggle) moves the chat into a window-sized tab and back. On Binary Ninja that is a tab of its own, one per window, and the Rikugan sidebar closes; on IDA the dock is tabbed beside the disassembly. The full-window panel shows ChatManager on its right with the chats of every database in databases::all(), what each one is doing, a “+ New chat” link per database and “Open a binary…”. Choosing a chat turns the panel to its database (setDatabase, then that chat). The list refreshes once per burst of ChatHub::chatsChanged / databasesChanged, and only while it is shown. Binary Ninja registers the database of every open tab when the full-window tab opens, and of each file opened while that tab exists.

System Prompt

buildSystemPrompt (agent/SystemPrompt.cpp) assembles the prompt once per omc session from embedded prompts/system/** files, in the order and with the placeholders given in prompts/MANIFEST.md:

  1. base.md, filled with the host's intro, tool_usage and capabilities.
  2. memory.md, with the first 200 lines of <database dir>/RIKUGAN.md after sanitizeMemory (20,000-char cap).
  3. current_binary.md, with the host's get_binary_info text after sanitizeBinaryContext. It is skipped when the profile hides binary metadata.
  4. available_tools.md, which lists the visible host tools and omc's built-ins.
  5. filesystem.md and shell.md, which describe omc's disk tools and bash: the scratch, binary and notes directories, and that each kind asks the user once per chat.
  6. databases.md when the chat can open other databases (Binary Ninja), and host_mcp.md when the database uses Binary Ninja's own MCP tools.
  7. The profile sections: singular analysis, custom instructions, restricted functions, the active profile and the IOC filters.

omc lists the skills to the model itself. Mode instructions (modes/*/explore.md) travel in the mode's prompts or in a subagent's task addendum, and the <rikugan_context> block (contextPrefix) is prepended to each user prompt.

06

Tools & Pipeline

Kinds

  • Host analysis tools are rk::ToolSpecs added in Host::registerTools (src/binja/tools/, src/ida/host/tools/, and src/ida/sdk/ for the ones that subclass SDK types). Their names, descriptions and parameters are the model-facing contract and stay 1:1 with the 1.x tools.
  • The chat tools in agent/ChatTools.cpp are ask_user, save_memory, spawn_subagent (depth 0 only), exploration_report and research_note (only while a mode shows them), and on Binary Ninja list_databases, open_database and ask_database (depth 0 only).
  • omc's built-ins are read, write, edit, ast_edit, grep, glob, bash, web_search and todo, which subagents do not get. MCP tools come from omc too. omc asks before each disk or shell call (tools.approval: prompt in the managed config.yml), and Permissions (agent/Permissions.h) intercepts that question. When the chat or a global setting already allows that kind of call, it answers at once; otherwise the transcript shows a permission card with Allow once, Allow for this chat and Deny. A chat's subagents share its permissions.
  • Binary Ninja's MCP tools (agent/HostMcp.cpp, binja/host/BnHostMcp.cpp) are the bn_* tools of Binary Ninja's own MCP server. Rikugan probes the server with an MCP handshake whatever ui.mcp.enabled says. It uses the address in Settings → MCP → Address (binja_mcp_url), or else Binary Ninja's ui.mcp.port / ui.mcp.endpoint, which default to 127.0.0.1:24642/mcp. HostMcpBar probes when a database or the panel shows, then after 2, 5, 10 and 30 s, then every 60 s until the server has answered once for that database. It stops after an explicit no, runs one probe at a time and keeps probes off the UI thread. Server tool descriptions are clipped to 140 characters, and parameter descriptions to 60.
  • The MCP tools are offered per database once the user agrees, through the panel's offer line or the header's MCP button, and the answer is remembered as hostMcp in the database's database.json. They are host tools with the server's own schema (ToolSpec::inputSchema, flag External). The server sends no readOnlyHint, so a tool whose name does not end in a reading verb (_list, _get, _info, _decompile ...) is Mutating. While they are on, Rikugan's own host tools are hidden for that database (chatToolVisible) and the chat tools stay. The server's active view is global, so HostMcp::call serializes calls and first selects the chat's view with bn_binary_view_set_active, found by file session id. The view switching tools and the file open, save and close tools are hidden.
  • McpClient speaks streamable HTTP over plain sockets and reads JSON or event-stream replies and chunked bodies. It starts a new session when the server forgot the old one, and Stop cancels it. A system-prompt change needs a new omc session, so toggling the MCP tools closes the database's idle sessions, which resume on demand. A busy session gets set_host_tools at once and closes when its run ends.

The flags in tools/Tool.h are Mutating, MainThread (every tool on IDA; UI and mutating tools on Binary Ninja), RequiresDecompiler, Cacheable, Script, Internal (undo pre-state readers, never shown), Exclusive, Blocking and External, which marks tools served by another program, as Binary Ninja's MCP tools are.

ToolDispatcher::execute

🚫
Gates
unknown/internal, profile denial, read-only phase, decompiler requirement
✋
Approval
scripts always; mutations with approve_mutations
📸
Pre-state
old name / comment / prototype for undo
⚙️
Run
cache lookup, then the handler (main thread if required)
🧼
After
mutation record, cache, marker strip, IOC filter, artifact cap
  1. An unknown or Internal tool returns an error.
  2. A tool the active profile denies returns an error.
  3. The mode phase gate applies: a read-only phase refuses Mutating and Script tools.
  4. A RequiresDecompiler tool returns an error when there is no decompiler.
  5. Script tools always ask, with Allow, Always allow for this chat and Deny.
  6. With approve_mutations on, the user is asked before each Mutating tool.
  7. The undo pre-state is captured for reversible mutations, by internal readers called through runDirect.
  8. The result cache is checked for list_functions, list_strings, get_binary_info, decompile_function and function_xrefs. It is a 64-entry LRU per database, flushed by any successful mutation.
  9. The tool runs, on the host main thread for MainThread tools. A ToolError becomes Error: <message>; other exceptions become Unexpected error: ... and are logged. A successful Mutating tool then calls Host::databaseChanged (so does /undo): IDA re-decompiles its open pseudocode views, which Hex-Rays does not redraw for a change made outside them. Binary Ninja's views redraw on their own.
  10. The mutation record is pushed to the chat's MutationLog.
  11. The result passes stripInjectionMarkers and then the profile's IOC filter. omc's own tools (files, shell, web, MCP servers) get the same treatment through omc_set_result_filter (SessionListener::filterToolResult).
  12. The artifact cap (capResult) applies. Over the tool's limit, the model gets the head (60%) and the tail (40%) plus the path of a file in <scratch>/artifacts/ with the whole text, which omc's read can page.

Partial output goes out as host_tool_update. The queue is bounded, and overflow and shutdown answer with an error.

07

Undo

  • Each chat has one MutationLog, kept in memory and shared with the chat's subagents.
  • The reversible tools are rename_function, rename_variable, set_comment, set_function_comment, set_pseudocode_comment, rename_address and set_function_prototype. Their pre-state (old name, comment or prototype) is read before the call, and a reversible tool's success text starts with “Renamed”, “Named” or “Set ”.
  • The known irreversible ones are recorded as such, and /undo reports “Cannot undo” for them: execute_python, the type creation and application tools, byte patches, IL and microcode transforms, optimizer and workflow installs, redecompile_function, and every Mutating tool of Binary Ninja's MCP server. A change that cannot be undone shows no Undo chip and is not counted as undoable.
  • /undo N pops records newest first on a non-UI thread. A reverse that can never succeed (UndoNoLongerPossible) is dropped; any other failure stops the undo and keeps the record. The result cache is flushed after a successful undo.
  • File changes made through omc's disk tools are not undone.

Modes

ModeDriver::start runs one busy job on the chat's session worker. It sends prompts in sequence and sets the phase in ChatContext, where read-only phases refuse mutations. Between prompts it shows the mode-only tools with set_host_tools. It counts turn_start frames to cap each phase, aborting the turn on overflow, and asks the user through decision cards.

After a cancelled mode, exploration_report and research_note stay shown until the next prompt finishes. Their ModeState carries a cancelledNotice that they answer with (“the run was cancelled; nothing recorded”), so a “continue” after Stop does not end in an unknown-tool error. The next mode run clears it.

Subagents & Bulk Renamer

omc's own task subagents cannot see host tools, so Rikugan runs its own (agent/Subagents.cpp). runSubagent opens a separate omc session, with its session dir under <sessions>/<db id>/subagents/, that gets the parent's database, tools, approvals, profile and mutation log at depth + 1, where spawn_subagent is no longer offered. The task is framed by prompts/agents/subagent.md plus an optional preset addendum (network_recon, report_writer) and perks, and a turn cap aborts runaway runs. SubagentRegistry tracks every subagent of the process with its live progress: the current tool, the tool count, tokens and a log of up to 200 entries. The transcript's task cards read it, and so does the agents panel, which shows the tree and the log and offers Stop, Steer, sending the summary to the chat, and “+ New agent”.

Bulk renamer

BulkRenamerEngine (agent/BulkRenamer.h) is driven by the bulk renamer page and the “Send to Bulk Rename” action.

  • In Quick mode the pending functions are decompiled one by one, with read_disassembly at the start, and each is cut to 6,000 chars. They are packed into batches of bulk_renamer_batch_size functions and at most 180,000 prompt chars, and each batch goes as one prompt to a tool-less, session-less omc worker session. Up to bulk_renamer_max_concurrent workers run at once. Replies are 0x<addr> <name> lines.
  • In Deep mode each function gets its own subagent (10 turns), which answers with RENAME: 0x<addr> <name>.
  • A run can be paused, resumed or cancelled, and cancelling aborts the in-flight sessions. Undo All restores the original names. Each batch or function is a subagent of category bulk_rename.
  • A rename the host answers with failure text (“No function at …”, “Failed to rename”) counts as failed (MutationLog::mutationSucceeded), and Undo All skips it.

Settings & Files

RikuganConfig (~/.rikugan/config.json; RIKUGAN_HOME overrides the root) is shared by both hosts. The Settings dialog has five tabs.

  • The Provider tab handles one provider at a time, as in Rikugan 1.x. The provider list is omc's get_login_providers plus the custom connections. For the selected provider the tab shows the account status, Log in (the same login sheet as the panel's “Connect a provider”), Log out and the API key, which is written to auth.json, then the provider's models (from get_available_models, which lists credentialed models only) and the thinking level. Custom connections, added and removed with +/−, hold a base URL, API type, key, model ids and, optionally, the context window and maximum output (0 keeps omc's default). They are written to models.yml, with contextWindow / maxTokens per model. Below them sit “Also use the logins of the omc command-line agent” (AuthSync) and local model discovery. omc's setup errors are reworded for Rikugan (omc/UserErrors.h) here and in the chat.
  • The Behavior tab covers auto context, restoring chats on start, not auto-loading chats, the session storage dir, the exploration turn limit, quiet retries, allowing file access and shell commands without asking, approving mutations, the bulk renamer's batch size and concurrency, and the Updates group (check_for_updates and Check now, see Updates).
  • The Skills tab enables and disables the built-in skills (a disabled one is removed from omc's skill dir) and lists the user's skills.
  • The MCP tab edits the servers in omc's mcp.json and, on Binary Ninja, the address of Binary Ninja's own MCP server (binja_mcp_url).
  • The Profiles tab has the built-in default and private profiles and the custom ones. A profile sets denied tools (Rikugan's and omc's built-ins), denied functions, hiding of binary metadata, IOC filter categories, custom regex rules, custom instructions and singular analysis.

Saving the dialog applies to open chats, as described under settings changes in the chat lifecycle.

AuthSync

“Use my omc logins” merges Rikugan's auth.json (R) with standalone omc's (O, in ~/.omc/agent/). Providers only in O are copied to R. For an OAuth login in both, the one that expires later wins on both sides, and for an API key in both, R's is kept. R-only entries never go to O, and nothing is deleted. Writes are atomic and 0600, and omc reloads credentials when R changed. AuthSync runs after each prompt, after a login and when Settings closes.

ExternalLogins

“Use my Claude Code / Codex login” (omc/ExternalLogins.h) is asked once, with links to the providers' policies. It shares the subscription logins of Claude Code (~/.claude/.credentials.json, or the macOS keychain item “Claude Code-credentials” when there is no file) and of the Codex CLI (~/.codex/auth.json) as R's anthropic and openai-codex OAuth credentials. A login is imported when R has none. For the same account the later expiry wins on both sides; refresh tokens are single-use, so a token omc refreshed is written back to the tool's file or keychain item with the other fields kept. An API key or another account's login in R is left alone. The sharing runs at start, after each prompt and when the option is turned on.

Updates

A release package updates itself from Rikugan's GitHub releases, and only when the user says so. update/Updater.h is the UI-thread side, one state machine per process under the module anchor. update/Update.h holds the blocking steps, which the updater runs on spawned threads. ui/console/UpdateBar.h is the panel's update line, and every panel shows the same state.

  • Only a build configured with -DRIKUGAN_UPDATES=ON knows its package name (binja-linux-x86_64, ida-windows-x86_64 ...). build.sh, build.ps1 and the release set it. Any other build has none (Updater::supported() is false), never checks, and Settings → Behavior greys the Updates group out.
  • Updater::start runs at plugin init. It deletes what an earlier update renamed aside (removeLeftovers), checks 20 s later, then every hour checks whether a day has passed since the last check (lastCheck in ~/.rikugan/update.json), while check_for_updates is on. Check now in Settings and Ctrl+K → Check for updates call check(true), which ignores the setting and shows the outcome even when nothing is newer.
  • A check is a HEAD request to <releases>/latest that follows the redirect. Only a landing on <releases>/tag/v<version> of the same site counts as a release, and its version is compared number by number with this build's. <releases> is https://github.com/buzzer-re/Rikugan/releases, or RIKUGAN_UPDATE_URL (the tests point it at a local server). When the plugin file on disk already carries the newer version, because another window installed it, the state goes straight to Installed.
  • The network and the archives go through the system's curl and tar (Windows 10 and later ship both), because IDA's Qt has no network module.

Installing

update::install runs on a spawned thread after the user's Update and reports each step to the update line.

  1. curl downloads rikugan-<version>-<package>.tar.gz (.zip on Windows), the asset the installers use, and its .sha256 into a temporary folder.
  2. The archive must match the SHA-256 in that file.
  3. tar unpacks it. plan() refuses links and anything that is not a regular file, and requires exactly one file with the plugin's own name, at the same place below the plugins folder as the installed one.
  4. That file must carry the release's version marker (RIKUGAN-VERSION:<version>, which every build embeds).
  5. Every new file is copied next to its place as <file>.rikugan-new, so nothing is touched unless all of them could be written.
  6. Each installed file is renamed aside to <file>.rikugan-old-<stamp> and the new one renamed into its place. Any failure puts every file back as it was. Windows lets a loaded DLL be renamed but not overwritten, so the old copy stays until removeLeftovers deletes it at the next start. Linux and macOS delete the old files at once, and the running process keeps its copy.

The host keeps the version it loaded until it restarts. A failure leaves the installed plugin as it was, and its reason goes to the update line and the host's log.

Security Model

Rikugan processes adversarial binaries, and strings, names and code from the sample reach the model and the UI.

  • Every tool result passes stripInjectionMarkers and then the profile's IOC filter: host tool results in ToolDispatcher, and the results of omc's file, shell, web and MCP tools through omc_set_result_filter. The stripping removes zero-width characters, role markers, chat template delimiters, the Anthropic magic string and instruction-override phrases, after normalising homoglyphs. Memory and binary context in the system prompt are sanitised and capped, and the cursor function name in the context block is stripped too. The system prompt's data-integrity section tells the model that tool output is data and carries no instructions.
  • execute_python, like any Script tool, always asks first and shows the code. It runs in the host's own Python (IDAPython, or Binary Ninja's scripting instance driven line by line) after prompts/python/guard_prelude.py, which sets up an AST blocklist and restricted builtins. The agent never runs the target binary.
  • omc's file and shell tools ask before their first use in a chat, per kind (read, write, edit, shell). “Allow for this chat” covers the chat and its subagents, and Settings can allow files or shell commands without asking. These tools are not sandboxed.
  • omc's settings are isolated from the sample. The session cwd is Rikugan's scratch dir and never the sample's directory, and project context files, rules and project MCP are off, so a sample tree cannot inject settings or start processes. omc commands that would chdir the host process are refused.
  • Credentials live in ~/.rikugan/omc/agent/auth.json (0600), written atomically, and models.yml with endpoint keys is 0600 as well. On Windows the files inherit the user profile's ACL (the user, SYSTEM and administrators).

Residual risks

  • Sanitisation is pattern-based and cannot catch every phrasing of an injection.
  • Once shell access is granted, an injected instruction can reach bash with the user's privileges, and file changes are not undoable.
  • The guard prelude is a blocklist inside the host's Python and does not sandbox anything: an approved script can do whatever the host can. Approving “Always allow” removes the per-script prompt for that chat.
  • MCP servers the user configures run as the user.
  • Binary Ninja's own MCP tools are not undoable. Their changes stay unless the user reverts them in Binary Ninja.

Building & Releases

Building without the hosts

-DRIKUGAN_SDK_ONLY=ON (what build.sh --sdk and build.ps1 -Sdk set) builds the plugins on a machine with neither IDA nor Binary Ninja installed. cmake/host_stubs.cmake and cmake/host_stubs.py link a probe of the plugin with the host's symbols left unresolved, then generate stand-in libraries that carry the hosts' real library names and exactly those symbols. Binary Ninja's core comes from the API's own stubs and its UI library from the probe. IDA's own libraries come from the SDK, and IDA's namespaced Qt is matched against the official Qt release of the same version. The plugins bind to the hosts' real libraries when the host loads them, as plugins built against an install do (verified in both hosts).

CI

.github/workflows/ci.yml runs on every push to main and dev-libomc and on every pull request, with one job per platform the release ships.

The only third-party action is GitHub's own upload-artifact, and checkout is plain git.

Releases

  • Pushing a tag v<version> runs .github/workflows/release.yml. The tag must match project(rikugan VERSION ...) in CMakeLists.txt and version in ida-plugin.json (ci.sh tag-check).
  • The five runners build both plugins and upload 20 packages (5 platforms × 2 hosts × package and -symbols package), each with its .sha256, to a draft release. The publish job adds SHA256SUMS over every file, checks that all 20 are there, and only then publishes the release as Latest.
  • Packages are stripped. The -symbols packages hold the debug information (a .debug file with a gnu-debuglink on Linux, a .dSYM on macOS, a .pdb on Windows) for reading a crash log's module+offset lines.
  • The release text is docs/releases/v<version>.md when it exists (what changed), then an install section and an asset table from build-tools/release_notes.sh, which previews it locally.
  • A manual run (Actions → Release → Run workflow) is a dry run: the same builds go to a draft named v<version>-dry-run-<run id>, which the cleanup job deletes. No tag is made and nothing is published.
  • install.sh / install.ps1 and the updater download these packages from the latest release.
